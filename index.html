Frame. Route. Handle.

Every request takes the same path. A codec cuts the bytes into frames, the router reads each envelope’s message ID, and that route’s middleware wraps its handler. The reply retraces the way it came.

Fragment reassembly is a transport step and optional. Message assembly, for protocols that spread one message across several frames, is a separate step that runs after it.

The stack, layer by layer

  1. Input

    Bytes off the socket

    A Tokio TCP stream. If the server expects a preamble, it is read and validated before any frame.

  2. Framing

    Cut at the length prefix

    A FrameCodec decodes frames. The default reads a 4-byte big-endian length prefix and refuses frames over 1,024 bytes.

  3. Reassembly Optional

    Fragments, rejoined

    With fragmentation enabled, fragments are rejoined before anything is decoded, bounded by size and by time.

  4. Envelope

    Read the envelope

    The serializer decodes an Envelope: a message ID, an optional correlation ID, and the payload bytes.

  5. Deflection

    Route by message ID

    One handler per ID. An ID with no route is logged and dropped; registering an ID twice fails at setup.

  6. Modulation

    Wrap the handler

    The route’s middleware wraps its handler, so it sees the request on the way in and the reply on the way out.

  7. Dwell

    Handle the message

    The handler runs with the envelope it was sent. In 0.3.0 it returns nothing; the default reply echoes the payload.

  8. Retrace

    Serialize, frame, send

    The reply keeps the request’s correlation ID and leaves through the serializer, optional fragmentation, and the codec.

What it carries

Any wire format, one trait

FrameCodec describes any wire format: how to cut frames, where the payload sits, and where a correlation ID lives.

  • Hotline20-byte header, big-endian lengths, a transaction ID
  • MySQL3-byte little-endian length, 1-byte sequence number
  • RESPTyped lines: simple strings, integers, bulk strings
00 00 00 0c12 payload bytes …

The default frame: a 4-byte big-endian length, then the payload. The three codecs above ship as worked examples.

Answer in middleware

A Transform wraps every route’s handler. Setup and teardown hooks carry per-connection state.

Large messages, bounded

Fragmentation, message assembly, and per-connection memory budgets that slow reads at 80% and close the connection past the cap.

One definition, both ends

WireframeClient correlates replies, reads streams, and pools warm sockets.

Test at the frame

Feed frames one byte at a time, fragment a payload, or pace a slow reader under paused time.

Push and streams, as parts

Priority push queues, a fair connection actor, and multi-frame responses, ready to drive.

The scope

Every frame is a stroke. A vector display draws only lines: the beam is steered from point to point, lit where it means something and blanked where it doesn’t. wireframe steers messages the same way. The codec cuts the byte stream into frames, the router deflects each one to exactly one handler, and where the beam stops, the trace burns brightest.

On every plate: mint is structure and the route in use, cyan is a frame, amber is traffic on the move, and magenta marks the one message being followed.

How the scope is drawn

Already carrying traffic

mxd, df12’s Hotline server, depends on wireframe 0.3.0. Its transport adapter frames and routes the Hotline protocol; its domain crate never imports wireframe. Hotline’s framing ships with wireframe too, as a worked codec example.

Warning

Pin tokio-util 0.7.19

wireframe 0.3.0 does not compile against tokio-util 0.7.20, which added a second Encoder for LengthDelimitedCodec. Pin the previous release in the lockfile until a fixed wireframe ships.
