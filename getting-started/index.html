The program on this page is a test in the site’s sample crate. It starts a real server on a loopback port, connects a real client, sends a Ping, and checks the Pong. Every panel below is cut from that file, and the crate runs against wireframe 0.3.0 with Rust 1.99.0.

Add the dependencies

wireframe runs on Tokio and, by default, encodes messages with bincode 2. The sample crate also uses async-trait to write middleware, and turns on two opt-in features: pool for client connection pools and testkit for the test drivers. Neither is needed for a first server.

Warning

Pin tokio-util before the first build

wireframe 0.3.0 fails to compile against tokio-util 0.7.20, which added a second Encoder implementation for LengthDelimitedCodec and made a conversion inside wireframe ambiguous (error E0283). A fresh dependency resolves 0.7.20. Pin 0.7.19 in the lockfile until a fixed release of wireframe ships:

Describe the messages

A message is any type bincode can encode and decode. Deriving bincode::Encode and bincode::BorrowDecode is enough: wireframe implements its Message trait for such types, which provides to_bytes and from_bytes. The message ID is not part of the type. It travels in the envelope, so the same type could be routed under any ID.

Route and answer

A route maps a message ID to a handler. In 0.3.0 a handler is an Arc’d closure that receives a reference to the envelope and returns a boxed future of (). It can inspect the request, log it, or hand work elsewhere, but it does not return the reply.

Replies are written in middleware. Each route’s handler is wrapped in a HandlerService, and the default service answers with the request’s own payload, so an unwrapped route is an echo. A middleware layer calls the inner service, then replaces the reply’s bytes.

With the middleware in place, the application is a route and a wrap. WireframeApp::new() is fallible, as is each builder step, so the whole chain returns wireframe::Result.

In 0.3.0

middleware::from_fn does not fit WireframeApp::wrap

The upstream user’s guide builds this middleware with middleware::from_fn. In 0.3.0 that does not compile: wrap accepts only a Transform whose output is a HandlerService, and from_fn produces a different service type. The Transform above is the pattern the upstream ping_pong example uses.

Serve it

WireframeServer::new takes a factory rather than an application: in 0.3.0 it calls the factory once for every accepted connection, so each connection starts from a freshly built application. Binding moves the server into its bound state; port 0 asks the operating system for a free port, and local_addr reports which one it chose. ready_signal fires once the workers are accepting, and run_with_shutdown stops them when its future completes.

Call it

The client shares the server’s defaults: the same length-delimited framing, the same bincode serializer, the same envelope. call_correlated stamps a fresh correlation ID on the request, sends it, reads the reply, and fails with ClientError::CorrelationMismatch if the reply carries a different one.

Where next

  • Route several message types, or route on a custom envelope.
  • Speak an existing wire format with a custom codec.
  • Layer middleware and keep per-connection state.
  • Test the application without opening a socket.
