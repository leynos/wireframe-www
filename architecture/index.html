Four nouns

wireframe keeps each layer’s vocabulary separate, so transport concerns do not leak into routing and routing does not leak into the domain.

Frame
The transport unit a FrameCodec cuts from the byte stream and writes back to it. It knows its own length and, perhaps, a correlation ID; it does not know what its payload means.
Fragment
A bounded slice of an oversized payload, with a header saying which message it belongs to and where it falls. Optional, and invisible above the transport.
Envelope
The routable wrapper decoded from a frame’s payload: a message ID, an optional correlation ID, and the payload bytes. Packet is the trait; Envelope is the bundled type.
Message
The typed value inside an envelope’s payload, encoded by the serializer. Bincode by default.

Inbound

  1. Accept. A worker accepts a TCP connection and builds an application from the factory.
  2. Preamble. If configured, a preamble of up to 1 KiB is decoded first; bytes read past it are replayed.
  3. Decode frames. The codec cuts frames from the stream.
  4. Reassemble. With fragmentation on, fragments are rejoined into whole payloads.
  5. Deserialize. The serializer decodes an envelope. Metadata-aware serializers can read routing fields without decoding the whole payload.
  6. Assemble. With a message assembler installed, protocol-level multi-frame messages are joined.
  7. Route. The message ID selects one route. No route: the message is logged and dropped.
  8. Middleware and handler. The route’s middleware stack runs, outermost first, around the handler.

Outbound

The reply takes the reverse path: back out through the middleware, rebuilt as an envelope with the request’s message ID and correlation ID, serialized, fragmented if it is too large and fragmentation is on, and wrapped by the codec. The order is fixed, so a reply is always fragmented before framing and never after.

Where state lives

Application-wideapp_data stores one value per type, shared by every connection the application serves
Per connectionThe value returned by on_connection_setup, handed to on_connection_teardown
Per middleware layerFields of the Transform, such as the counter in the middleware guide
Across connectionsSessionRegistry, holding weak push handles by connection ID

What 0.3.0 does not do

A frank list, because every one of these appears somewhere in the upstream design documents:

  • Handlers do not return replies or take extractors. Replies are written in middleware.
  • middleware::from_fn cannot be passed to WireframeApp::wrap.
  • The routed server path sends one reply per request. Push queues, the connection actor, streaming responses, and WireframeProtocol hooks are not driven by it.
  • Codec recovery policies and the on_eof hook are defined but not consulted.
  • The read timeout does not close idle connections.
  • There is no built-in TLS.

The roadmap says what is in progress.
