Four nouns

wireframe keeps each layer’s vocabulary separate, so transport concerns do not leak into routing and routing does not leak into the domain.

Frame
The transport unit a FrameCodec cuts from the byte stream and writes back to it. It knows its own length and, perhaps, a correlation ID; it does not know what its payload means.
Fragment
A bounded slice of an oversized payload, with a header saying which message it belongs to and where it falls. Optional, and invisible above the transport.
Envelope
The routable wrapper decoded from a frame’s payload: a message ID, an optional correlation ID, and the payload bytes. Packet is the trait; Envelope is the bundled type.
Message
The typed value inside an envelope’s payload, encoded by the serializer. Bincode by default.

Inbound

  1. Accept. A worker accepts a TCP connection. The application was prepared once, before the server reported readiness, and every connection shares it.
  2. First read. The server reads first, under a 10-second deadline by default: a preamble of up to 1 KiB if one is configured, otherwise a first byte. Bytes read past it are replayed.
  3. Decode frames. The codec cuts frames from the stream.
  4. Deserialize. The serializer decodes an envelope, which must fill the frame exactly. A metadata-aware serializer can read routing fields first, but the framework still deserializes fully unless should_deserialize_after_parse returns false.
  5. Reassemble. With fragmentation on, fragments carried in envelopes are rejoined into whole messages.
  6. Assemble. With a message assembler installed, protocol-level multi-frame messages are joined.
  7. Route. The message ID selects one route. No route: the message is logged and dropped.
  8. Middleware and handler. The route’s middleware stack runs, outermost first, around the handler.

Outbound

The reply goes back out through the middleware and is rebuilt as an envelope with the request’s message ID and correlation ID. It is then fragmented if it is too large and fragmentation is on, and each piece is serialized, wrapped by the codec, passed to before_send, and encoded. The order is fixed, so each fragment is its own frame.

Where state lives

ScopeMechanism
Application-wideValues captured by handler and middleware closures. app_data stores values for the extractor building blocks, but nothing reads it while serving, so it never reaches handlers
Per connectionThe value returned by on_connection_setup, handed to on_connection_teardown
Per middleware layerFields of the Transform, such as the counter in the middleware guide
Across connectionsSessionRegistry, holding weak push handles by connection ID. The application inserts them; nothing populates it automatically

What this release does not do

A frank list, because every one of these appears somewhere in the upstream design documents. Several parts ship ahead of the runtime that will use them, and the users’ guide says how far each goes:

  • Handlers do not return replies or take extractors, and app_data and request bodies do not reach them. Replies are written in middleware.
  • middleware::from_fn cannot be passed to WireframeApp::wrap.
  • The routed server path sends one reply per request. Push queues, the connection actor, and streaming responses are not driven by it, and of the WireframeProtocol hooks it runs only before_send.
  • Codec recovery policies and the on_eof hook are defined but not consulted.
  • The read timeout does not close idle connections, and shutdown waits for them with no deadline.
  • There is no built-in TLS.

On main since the candidate Every server connection runs a ConnectionActor, route_response handlers return a Response that can stream, and on_command_end, handle_error, and stream_end_frame run. ADR 0017 removes the extractors and app_data. on_eof, recovery policies, push queues, and request bodies are still not driven. What main has changed
