Enable the testkit

The testkit feature adds wireframe::testkit: drivers that run a real WireframeApp over an in-memory duplex stream, with no socket and no server. A driver encodes requests with a codec, feeds the bytes in, and returns the decoded replies. Turn the feature on for tests only, through a dev-dependency or a feature of the crate under test.

Every sample on this site that does not need a real socket is tested this way, including the routing, codec, and middleware guides.

One byte at a time

TCP delivers bytes, not frames. A codec that only works when a frame arrives in one read is a codec with a bug waiting for a busy network. drive_with_partial_frames concatenates the encoded requests and writes them in chunks of a chosen size, down to one byte:

The helper builds requests by serializing an Envelope with BincodeSerializer, the application’s default. The echo application returns each request unchanged, so the replies equal the requests. drive_with_partial_codec_frames returns decoded codec frames instead of payloads, for checking header fields.

Feed fragments

drive_with_fragments takes a raw payload and a Fragmenter, fragments the payload, wraps each fragment in an envelope, and feeds the frames through the application. The fragmentation guide’s sample uses it with a 2,000-byte request and 256-byte fragments. drive_with_partial_fragments combines both drivers, fragmenting and then chunking.

Note

The fragment driver addresses message ID 1

The envelopes the fragment driver builds carry message ID 1, so the application under test needs a route there.

wireframe::testkit::reassembly adds assertions over reassembly and message-assembly state, such as whether a message is still incomplete, how many bytes are buffered, and which error ended an assembly. They return a result rather than panicking, so they work in rstest tests and in rstest-bdd steps.

Slow readers and writers

Back-pressure only shows up when something is slow. SlowIoPacing sets a chunk size and a delay between chunks, and SlowIoConfig applies one pacing to the writer, another to the reader, and a duplex capacity small enough to fill:

The test runs with #[tokio::test(start_paused = true)], so the delays advance virtual time and the test finishes at once. A small capacity and a paced reader are what make the application’s writes wait.

Beyond the testkit

The separate wireframe_testing crate, also at 0.3.0, re-exports the testkit and adds more: codec-aware drivers that return payloads or frames for any codec, Hotline-framed fixtures for valid, oversized, truncated, and correlated frames, an observability handle that captures logs and metrics together, and a harness that starts a real server and a connected client in one test. This site’s samples use only the main crate’s testkit; the crate’s own documentation covers the rest.

For servers and clients that must meet over a real socket, the getting-started program is itself a pattern: bind to port 0, read local_addr, wait on ready_signal, and stop with run_with_shutdown.
