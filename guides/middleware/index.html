Write a Transform

Middleware in wireframe follows the Tower and Actix shape. A Service turns a ServiceRequest into a ServiceResponse; a Transform wraps one service in another. WireframeApp::wrap takes any Transform whose output is a HandlerService, the type every route’s handler is held in.

The layer below counts every request on every route. It is generic over the envelope type, so it works with a custom Packet as well as Envelope. HandlerService::from_service keeps the route’s ID while swapping in the wrapping service.

Both traits are async_trait traits in 0.3.0, so implementations need the async-trait crate.

Order and scope

  • Per route. The application wraps each route’s handler in the full middleware stack when it builds its routes. The router chooses the route first, so a message with an unknown ID never reaches middleware.
  • First registered, outermost. The first wrap sees the request first and the reply last. In the sample application, the version upgrade runs before the counter.
  • Infallible. The routed path expects Error = Infallible: a layer that cannot proceed writes an error reply rather than returning an error.

Write the reply

A routed handler returns nothing, and the default HandlerService answers with the request’s payload. Replies are therefore written by middleware: call the inner service, then replace the bytes through ServiceResponse::frame_mut(). Getting started builds a full Ping to Pong layer this way. The reply keeps the request’s message ID; see correlation IDs for what happens to its correlation ID.

A handler that needs to influence the reply has to share state with the middleware, for example through a channel or a value the middleware can read. The upstream README describes extractor-style handlers that return their reply; they are not in 0.3.0.

What from_fn is for

middleware::from_fn turns an async function into a Transform, and the upstream user’s guide passes one to wrap. In 0.3.0 that does not compile: from_fn’s output is an FnService, not a HandlerService, so it fails wrap’s bound. It can still wrap a service directly, inside a handwritten Transform that hands the result to HandlerService::from_service, but for routed middleware a handwritten Transform is the shorter path.

Accept two versions

Middleware can rewrite a request before the handler sees it. This layer upgrades a legacy message format so the handler only ever sees the current one. It tries the current format first. That test only works because version 2 added a field, so a version 1 payload is too short to decode as version 2: bincode carries no type information, and two formats with the same layout decode as each other without complaint. The sample asserts the difference before relying on it.

In the sample, a version 1 point goes in and the echoed reply decodes as version 2. A production version of this layer would also count legacy traffic, so the old format can be retired when the count reaches zero.

Connection setup and teardown

on_connection_setup runs once when a connection starts and returns a value of any type. That value is held for the life of the connection and handed to on_connection_teardown when the stream ends. Registering a setup hook changes the application’s connection-state type parameter.

Both hooks are async. Setup runs before any frame is read, after a preamble if the server expects one. The handlers and middleware in 0.3.0 have no access to this state; it is for per-connection bookkeeping such as metrics, registration, and cleanup.

The WireframeProtocol trait, installed with with_protocol, defines further hooks around outbound frames and stream ends. Its hooks are run by the connection actor, which the routed server path does not use yet; see the connection actor.
