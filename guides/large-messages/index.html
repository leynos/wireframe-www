Fragmentation and memory budgets

Large messages cross the wire in pieces and are rejoined before a handler sees them, inside budgets the connection cannot exceed.

Turn fragmentation on

A frame has a size limit, 1,024 bytes by default, and some messages are larger. Fragmentation splits an oversized payload into fragments that each fit a frame, then rejoins them on the far side before routing, so handlers only ever see whole messages. It is off by default. enable_fragmentation() derives a configuration from the frame limit: messages up to sixteen frames’ worth (16 KiB by default), partial messages evicted after 30 seconds, and caps on how much a peer can leave unfinished. Both ends must speak this format, and WireframeClient does not: a client talking to a fragmenting server sees FRAG payloads.

The layering is fixed. Outbound, a reply is fragmented, then each fragment is serialized, wrapped by the codec, passed to before_send, and encoded, so each fragment is its own frame. Inbound, each frame is decoded and deserialized as an envelope, then fragments are reassembled and protocol messages assembled, and only then is the result routed. Each fragment carries a FragmentHeader (message ID, index, and a last-fragment flag) behind a FRAG marker.

fragmentation(Some(config)) sets limits explicitly; FragmentationConfig::for_frame_budget builds one from a frame size, a maximum message size, and a reassembly timeout. Remember that changing the codec or buffer_capacity clears it.

A message over max_message_size counts as a deserialization failure. Exceeding max_concurrent_partials or max_buffered_bytes closes the connection immediately.

Message assembly is different

Fragmentation is wireframe’s own transport mechanism, invisible to the protocol. Some protocols define their own multi-frame messages instead, with a first frame and continuations in their own header format. For those, a MessageAssembler, installed with with_message_assembler, parses each frame’s header into a first frame or a continuation, keyed by a MessageKey.

Assembly runs after fragment reassembly and before dispatch. It can hold several messages open at once, interleaved on one connection, and, where the protocol numbers its continuations, it rejects gaps, duplicates, and frames after the last. A message that completes is routed as usual.

A declared total_body_len is a commitment. A body that does not match it is rejected, counted as a deserialization failure, and never reaches a handler, and None opts out. An exact total is also the cheapest way to refuse an oversized message early.

Memory budgets

Partial messages cost memory, and a peer can send first frames forever. MemoryBudgets caps three things per connection: the bytes buffered for one message, for the whole connection, and across messages in flight. Without explicit budgets, wireframe derives them from the frame limit: 16, 64, and 64 times it, which is 16, 64, and 64 KiB by default.

TierWhenWhat happens
Per frame, with a MessageAssembler onlyA frame would push buffered bytes past a capThe frame is rejected, that partial message is freed, and the failure counts as a deserialization failure
Soft limitBuffered bytes reach 80% of the smaller aggregate capThe connection pauses briefly before reading the next frame, pushing back on the sender
Hard capBuffered bytes exceed the smaller aggregate capThe connection closes

The soft limit and the hard cap count fragment and assembly bytes together, so a workload that fragments heavily can pace or close even with message assembly off. A default application buffers neither, and these tiers have nothing to do. The effective per-message limit is the smaller of the fragmentation maximum and the per-message budget. A message that completes in a single frame is never counted, because nothing is buffered.
