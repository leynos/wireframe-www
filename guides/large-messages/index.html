Fragmentation and memory budgets

Large messages cross the wire in pieces and are rejoined before a handler sees them, inside budgets the connection cannot exceed.

Turn fragmentation on

A frame has a size limit, 1,024 bytes by default, and some messages are larger. Fragmentation splits an oversized payload into fragments that each fit a frame, then rejoins them on the far side before anything is decoded. It is off by default. enable_fragmentation() derives a configuration from the frame limit: messages up to sixteen frames’ worth (16 KiB by default), and partial messages evicted after 30 seconds.

The layering is fixed. Outbound, a reply is serialized, then fragmented, then wrapped by the codec. Inbound, frames are decoded, then reassembled, then deserialized, so handlers always receive whole envelopes. Each fragment carries a FragmentHeader (message ID, index, and a last-fragment flag) behind a FRAG marker.

fragmentation(Some(config)) sets limits explicitly; FragmentationConfig::for_frame_budget builds one from a frame size, a maximum message size, and a reassembly timeout. Remember that changing the codec or buffer_capacity clears it.

Message assembly is different

Fragmentation is wireframe’s own transport mechanism, invisible to the protocol. Some protocols define their own multi-frame messages instead, with a first frame and continuations in their own header format. For those, a MessageAssembler, installed with with_message_assembler, parses each frame’s header into a first frame or a continuation, keyed by a MessageKey.

Assembly runs after fragment reassembly and before dispatch. It can hold several messages open at once, interleaved on one connection, and, where the protocol numbers its continuations, it rejects gaps, duplicates, and frames after the last. A message that completes is routed as usual.

Memory budgets

Partial messages cost memory, and a peer can send first frames forever. MemoryBudgets caps three things per connection: the bytes buffered for one message, for the whole connection, and across messages in flight. Without explicit budgets, wireframe derives them from the frame limit: 16, 64, and 64 times it, which is 16, 64, and 64 KiB by default.

TierWhenWhat happens
Per frameA frame would push buffered bytes past a capThe frame is rejected, that partial message is freed, and the failure counts as a deserialization failure
Soft limitBuffered bytes reach 80% of the smaller aggregate capThe connection pauses briefly before reading the next frame, pushing back on the sender
Hard capBuffered bytes exceed the smaller aggregate capThe connection closes

The effective per-message limit is the smaller of the fragmentation maximum and the per-message budget. A message that arrives in a single frame is never counted against the aggregate caps, because nothing is buffered.
