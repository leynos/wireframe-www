What the server wires up

Start with the boundary, because it decides what can be built today. In 0.4.0-alpha1, a connection served by WireframeServer answers each routed request with one reply, split across frames only by fragmentation. The types on this page, which are Response, PushQueues, ConnectionActor, and SessionRegistry, ship, are tested, and work together. WireframeServer does not drive them, so adopting one means writing the glue.

On main since the candidate The server runs a ConnectionActor for every connection, and a handler registered with route_response returns a Response, so streamed and multi-packet replies reach the wire. Push queues and SessionRegistry are still not exposed by the server. What main has changed

Proposed · RFC 0004

Give each direction room to move. The proposed session driver coordinates reads, writes, application work, and cancellation, subject to finite capacity and explicit progress assumptions. Review the proposal

In 0.4.0-alpha1

Building blocks, not yet a server feature

Server-initiated pushes and multi-frame replies on a WireframeServer connection need a connection loop that runs the actor. That integration is upstream roadmap work, tracked for the actor and streaming responses and for push queues and the session registry. The users’ guide says how far each part goes. The client side is further along: call_streaming already reads a multi-frame reply from any server that sends one.

Responses that stream

Response describes a reply of any shape: Single frame, a Vec of frames, a Stream of fallible frames, a MultiPacket channel, or Empty. into_stream turns any of them into one boxed stream, which is the form the connection actor consumes.

Back-pressure through a channel

Response::with_channel returns a sender and a MultiPacket response around the matching receiver. A producer task sends frames whenever it has them. Each send waits while the channel is full, so a slow consumer slows the producer instead of growing a buffer. Dropping the last sender ends the response.

A protocol marks the end of such a stream with a terminator frame: the connection actor takes it from the stream_end_frame protocol hook, and the client recognizes it through Packet::is_stream_terminator.

Priority push queues

PushQueues holds frames a connection should send without being asked: notifications, heartbeats, broadcast traffic. The builder sets a high- and a low-priority capacity, an optional rate limit, and an optional dead-letter queue. The rate limit defaults to 100 pushes a second, accepts up to 10,000, and is shared by both queues; unlimited() removes it.

The builder returns the queues and a cloneable PushHandle. Background tasks push through the handle: push_high_priority and push_low_priority wait for the rate limiter and then for room, while try_push skips the limiter and applies a PushPolicy instead of waiting, optionally warning and forwarding the frame to the dead-letter queue. DropIfFull without a dead-letter queue loses frames silently.

The connection actor

ConnectionActor drains a connection’s push queues and its current response into one ordered output, polling a cancellation token so it stops promptly on shutdown. High-priority frames go first, but FairnessConfig lets a low-priority frame through after at most eight high-priority ones by default, optionally after a time slice as well, so a busy high queue cannot starve the low one.

run collects frames into a Vec the caller supplies, and does not write to a socket. The actor also runs the WireframeProtocol hooks installed with with_protocol. On a WireframeServer connection, which has no actor, only before_send runs; the others have no effect there.

Find a connection later

SessionRegistry maps a ConnectionId to a connection’s PushHandle so that other tasks can reach it. It holds each handle weakly: when the connection’s queues are dropped, the entry no longer resolves, and stale entries are pruned on lookup or by prune(). It is not populated automatically: it tracks the handles the application inserts.

SessionRegistry::default() requires the frame type to implement Default. Envelope does not, so in 0.4.0-alpha1 a registry of envelope handles needs a frame type that does, or a wrapper.
