The defaults

A new application frames with LengthDelimitedFrameCodec: a 4-byte big-endian length prefix, then the payload, with frames over 1,024 bytes refused. Everything inside the frame is bincode, and the connection loop wakes every 100 ms to clear stale partial messages.

buffer_capacity raises or lowers the frame limit for the length-delimited codec. codec() returns the installed codec, which is how the sample checks the change took effect:

Note

Changing the codec resets fragmentation

buffer_capacity and with_codec both clear any fragmentation settings, because the fragment size depends on the frame limit. Call enable_fragmentation() after them, not before.

Write a FrameCodec

A protocol with its own framing implements FrameCodec. The trait owns a Tokio Decoder and Encoder for its frame type and tells wireframe four things about a frame: where its payload is, how to wrap an outgoing payload, where a correlation ID lives if the header carries one, and how large a frame may be.

The example below is a small invented protocol: two bytes of length, four bytes of tag, then the payload. The decoder waits until a whole frame has arrived, refuses one that exceeds the limit, and splits the payload off without copying it.

frame_payload_bytes is optional. Its default copies the payload slice; overriding it to clone a Bytes hands the payload on with a reference-count increment instead. correlation_id is consulted only when the decoded envelope has none of its own.

Install it

with_codec swaps the codec and changes the application’s type. wireframe clones the codec for each connection, so a codec that keeps state, such as a sequence counter, should make sure a clone starts fresh.

The sample then feeds an encoded request through the testkit one byte at a time. The decoder returns nothing until a whole frame has arrived, and the reply comes back intact.

wireframe ships three worked codecs in its repository, for Hotline, MySQL, and the Redis serialization protocol (RESP). They are listed on the examples page. The Hotline codec is also reachable as wireframe::codec::examples::HotlineFrameCodec, though that module is hidden from the API reference.

Read a preamble first

Some protocols open with a handshake before any frame: a magic number, a version, a client name. The server reads it with with_preamble::<T>(), where T is any bincode type, decoding at most 1 KiB. Bytes read past the preamble are replayed into the framing layer, so nothing is lost.

The success handler receives the decoded preamble and the raw TCP stream, so it can reply before framing starts. The client sends its preamble with with_preamble as soon as it connects:

In 0.3.0

A success handler cannot reject the connection

An error returned from on_preamble_decode_success is logged, and the connection carries on to the application. A preamble that fails to decode, or does not arrive within preamble_timeout, goes to on_preamble_decode_failure instead, and the connection closes after it runs. Validate fields that matter, such as a magic number, in a type that fails to decode when they are wrong, or close the stream from the handler.

Codec errors

In 0.3.0 the connection loop treats a decoder error as fatal: the connection closes. For the default codec that includes a frame over the limit. A frame that decodes but whose payload is not a valid envelope is different: it counts towards the limit of ten consecutive deserialization failures described in the routing guide.

In 0.3.0

Recovery policies are defined but not consulted

The wireframe::codec module defines a richer taxonomy (CodecError, with framing, protocol, I/O, and end-of-stream variants), a RecoveryPolicy of drop, quarantine, or disconnect, a RecoveryPolicyHook trait, and an on_eof protocol hook. The 0.3.0 server does not call any of them, so implementing one changes nothing yet.
