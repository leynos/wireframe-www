Register routes

A route is a u32 message ID and the handler that receives messages carrying it. WireframeApp::route takes both and returns the builder, so routes chain. A handler’s type is Handler<Envelope>: an Arc around a closure that takes &Envelope and returns a pinned, boxed future of ().

Each ID has one handler. Registering an ID a second time is an error at setup, not a silent replacement, so a dispatch table can never be ambiguous:

The bundled envelope

Unless told otherwise, an application decodes every frame into Envelope: a message ID, an optional correlation ID, and the payload bytes. The router reads only the ID. The payload is opaque until something decodes it, usually with Message::from_bytes in middleware.

Correlation IDs

The correlation ID ties a reply to its request. In 0.3.0 the reply is rebuilt with the request’s message ID and passed through PacketParts::inherit_correlation: if middleware left the correlation ID unset, the request’s is copied across, and if middleware set a different one, the request’s wins and a warning is logged. When an envelope arrives without a correlation ID, a codec that carries one in its frame header supplies it instead.

A None correlation ID means an unsolicited frame, such as a server push. Use None rather than Some(0).

On the client, call_correlated generates the ID and rejects a reply that does not carry it back. See the client runtime.

Unrouted and malformed traffic

The router answers only what it can route. In 0.3.0:

  • A message whose ID has no route is logged at warning level and dropped. The peer gets no reply.
  • A frame that does not decode as an envelope counts as a deserialization failure. Ten in a row close the connection; any successful frame resets the count.
  • Routes are fixed when the application is built. Adding one later means building another application.
